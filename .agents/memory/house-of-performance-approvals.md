---
name: House of Performance design approvals
description: Brand direction and staged approval boundaries for the FSD website refinement
---

FSD’s website direction is “THE HOUSE OF PERFORMANCE,” with the philosophy “Luxury in its expression. Performance in its purpose.” Preserve the campaign statement “BUILT FOR THE DRIVE WITHIN.”

**Why:** The user wants a distinctive luxury performance house spanning apparel, modest combat, technology concepts, equipment and future flagship experiences, not a generic fitness retailer.

**How to apply:** Use the existing FSD photography and approved shield-led asset in isolated proposals. Do not generate substitute product imagery, redesign branding, rename products, overwrite originals or rebuild the site from scratch.

The user chose Homepage B and header-attached navigation for refinement. Homepage B+ remains unapproved. For the Phase 3 navigation, the user later explicitly directed a targeted reconstruction from their supplied visual recording. Category selection reveals subcategories without scrolling; navigation follows only a deliberate destination choice.

**Why:** The user directly authorized a targeted live navigation reconstruction from the visual reference; that authorization does not extend to a homepage or catalogue redesign.

**How to apply:** Use the recording for navigation structure and the current site data for destinations. Keep Homepage B+ staged, preserve the existing catalogue and product assets, and do not publish or enable checkout.

The homepage should combine a dark, cinematic, powerful hero with sophisticated editorial composition and generous whitespace. Obsidian black, graphite and champagne gold are primary; porcelain is selective contrast, not the dominant background. Apparel should feel like luxury fashion campaigns, while Bio-Lab™ and Hardware retain performance and engineering credibility.

**Why:** The user explicitly requested luxury fashion-house presentation with authentic athletic performance and technological innovation, rather than a predominantly light website.

**How to apply:** Refine isolated proofs using the existing approved logo and product imagery; do not overwrite assets. Keep the overall design minimalist, confident, sophisticated and premium.

Navigation must remain integrated with and attached to the header, using graphite or soft black, very subtle translucency and restrained champagne accents. Avoid thick gold borders, oversized panels, excessive blur and flashy animation. The user requested smooth opening and closing of approximately 180–250 milliseconds, with an easy-to-use expanding mobile navigation sheet.

**Why:** The user wants the clarity of a premium technology brand with a luxury fashion-house finish, not a detached pop-up.

**How to apply:** Keep Men’s Performance, Women’s Modest Combat, Bio-Lab™ and Hardware readily discoverable. Preserve the existing collection structure and ensure relevant subcategories are immediately available without automatic page scrolling.

The supplied recording is a visual reference, not a Git checkpoint or source-code proof. The original implementation was not identified. The user explicitly requested a targeted reconstruction of Phase 3 navigation from the recording; do not claim source recovery.

**Why:** The user clarified that no checkpoint containing the original source was identified, then directed an accurate reconstruction while preserving the existing website and catalogue.

**How to apply:** Limit changes to header navigation, use current catalogue data for destinations, do not reuse later sandbox prototypes as original source, and do not revert the whole project.

During the weighted-rope recovery request, the user explicitly authorized restoring the existing one-product draft with the nine supplied images: one fixed campaign image and eight complete, unsplit 2 × 2 edition boards. This approval is for an internal draft preview only; it does not supply a public product ID, verified price/specifications, stock, checkout approval or publication approval.

**Why:** The user approved recovering the draft from history and using the exact newly supplied artwork, while requiring an internal review before any public catalogue use.

**How to apply:** Keep the historic product key, leave the public ID and unknown facts unset, preserve all source images unchanged, never crop or split edition boards, and keep purchasing/publication disabled. Do not change Phase 3 navigation or other catalogue records unless the user later explicitly authorizes a specific exception.

The user subsequently authorized one targeted exception: place the FSD Weighted Skipping Rope draft under Hardware → Strength Equipment, with its menu item and feature CTA opening the existing private preview. Keep that entry and preview development-only; the active catalogue, production navigation, and purchase flow remain unchanged.

**Why:** The user explicitly requested this exact navigation placement and review path while requiring the product to remain a non-purchasable draft.

**How to apply:** This exception applies only to the weighted-rope preview. Keep its public ID, price, verified specifications, SKU and stock unset; do not generalize the authorization to other products or publish the website.

The user authorized a React + Tailwind migration while preserving the current flagship layout, six-tab navigation, catalogue, and approved asset boundaries. For this build, use Obsidian `#090A0C`, Champagne Gold `#C8AA72`, and 16px glass blur. Checkout remains disabled until product readiness is confirmed; internal financial metrics must stay off customer-facing pages.

**Why:** The user directly selected React + Tailwind and specified that the primary flagship design must remain intact; they also explicitly chose to keep checkout disabled and financial data internal.

**How to apply:** Keep new UI work inside the existing visual system. Do not replace the flagship template, publish unverified product information, activate checkout, or show COGS, margins, or projected profit to customers.

React route state should resolve to real FSD collection, product, section, or private-preview destinations; do not use placeholder route screens or checkout controls.

**Why:** The user approved the AppRouter approach only when it uses real FSD routes and preserves the current storefront and checkout hold.

**How to apply:** Keep the route state synchronized with the existing destination behavior while the UI migration proceeds. Reuse real catalogue and section views; do not invent product data, replace the flagship layout, or activate purchasing.

Keep any React host around the sticky navigation layout-transparent so it does not constrain the header’s sticky positioning.

**Why:** A normal block wrapper limited the sticky header to the wrapper’s short height, breaking its pinned behavior after scrolling.

**How to apply:** When migrating header navigation, verify sticky behavior after scrolling and avoid introducing a height-limited containing block.

When new concept pages or sections have media or copy pending review, keep their routes and navigation available and show the complete responsive structure with clearly titled, styled placeholders. Do not select unverified media or hide unfinished sections.

**Why:** The user explicitly wants the full desktop and mobile journey visible for review while assets and claims are still being approved.

**How to apply:** Use consistent placeholder dimensions and the existing FSD visual system. Keep product claims, asset mappings, account flows, sign-ups, and checkout within their separate approval boundaries.

The user designated the existing storefront structure as the master baseline: integrate future work additively, preserve the three-column menu and editorial page flow, keep pending concepts visibly marked and non-purchasable, and retain the gold scroll progress indicator.

**Why:** The user explicitly described the current site as the definitive baseline and directed that future additions must not trigger a broad rewrite; the gold indicator must remain functional across pages.

**How to apply:** Make focused changes within the current navigation and page hierarchy. Preserve the story section’s editorial placement, concept/pre-launch safeguards, and the global gold progress indicator when adding or revising features.

The user chose to adapt their supplied top-navigation snippet to the existing header and menus, not replace the data-driven navigation with its demo markup.

**Why:** The snippet was incomplete and included placeholder panels and page sections; the user selected adaptation to the current platform.

**How to apply:** Preserve the approved menu structure, real destinations, keyboard/focus behavior, mobile links, and motion settings. Apply reference behavior to the shared header only, reserving its layout space so fixed navigation does not cover page content.

The user explicitly authorized the complete supplied FSD The House website, including its interactive router and data dictionary, as a public page linked from THE HOUSE navigation.

**Why:** The user asked for direct integration into the main project with no private framing, requested production publication, and confirmed UK legal advice cleared this specific supplied page for public circulation.

**How to apply:** Keep this page and its supplied content publicly accessible at its dedicated route. Do not generalize this approval to unrelated drafts, unverified claims, checkout, or other private concepts.

For newly added House destinations, the user chose to preview not-ready pages in development and disable their links and routes in production until they are approved.

**Why:** The user wants the complete House journey available for internal review without presenting unfinished pages as public content.

**How to apply:** Keep current approved pages public. Show explicit draft status in development; do not publish unfinished Founder, Flagship, Investor, or other unapproved content, and do not infer approval from the broader House-page authorization.

The House disclosure is a destination index, not a container for page bodies. Every destination must load at its own URL, and scrolling must remain within that page. Keep the approved homepage story section outside the route index.

**Why:** The user explicitly requested independent House pages with no stacked sibling content while preserving the homepage and existing mega-menus.

**How to apply:** Keep the House view to navigable links. Do not append full destination sections to the homepage or menu overlay. Continue to show development-only draft status and block unapproved routes from production.
